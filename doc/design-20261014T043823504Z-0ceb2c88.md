# rs-websocket 请求头、入站背压与文档契约修复设计

> 日期：2026-10-14。目标版本：`qubit-websocket` 0.1.0。状态：已实施。验证日期：2026-10-14；已通过项目格式对齐、格式与样式检查、全量测试、Clippy、Rustdoc 和 `.infra/bin/ci-check.sh`。关联[实施计划](implementation-plan-20261014T043823504Z-0ceb2c88.md)。

## 目标与范围

本轮修复同名多值请求头在握手请求中丢失的问题，明确并测试入站队列满时的关闭策略，使 Rustdoc、双语 README、双语用户指南及设计文档的状态描述与实现一致。保持 WebSocket 客户端、双向有界队列、TLS 验证、单接收者和克隆发送者的现有架构。无需新增公开 API；用户已允许必要的破坏性变更，但本方案没有依赖破坏性变更。

`rs-web` 仍只作为本仓库互通测试的服务端。本机可见的其他 `rs-*` 生产代码没有直接依赖 `qubit-websocket`，因此不规划下游源码迁移；集成测试仍须覆盖与 `qubit-web` 的现有交互。自动重连、代理、压缩和服务端能力不属于本轮。

## 已确认的现状

- `src/client.rs::apply_user_headers` 遍历 `HeaderMap` 的每个值，却对目标调用 `insert`。同一名称的前一个值会被后一个值替换；`WsClientBuilder::headers` 和 `WsClient::connect_with` 都经过此路径。现有握手测试只验证单值头。
- `src/session/driver.rs::enqueue_while_polling_control` 在入站 `push` 等待容量时继续读取控制帧。若此时读到下一条文本或二进制消息，立即返回 `SlowConsumer`；若未读到额外业务消息，达到 `no_progress_timeout` 后也返回该结果。写侧尝试发送 `1013` Close，终态为 `WsErrorKind::Timeout`。现有测试覆盖 `1013` 和 Ping/Pong，但双语指南的“等待应用继续消费”没有说明额外业务消息会提前触发关闭。
- `src/lib.rs` 的示例将 `Closed { code: Some(1000) }` 输出为“subscription completed”，而 README 和指南明确要求由应用协议判断业务完成。
- 实施开始前，`doc/design-20261014T021031598Z-49c7bedd.md` 仍写“待实施方案”，但其关闭协调与错误接口已在源码和测试中实现。中英文架构文档将它作为实施设计链接，读者可能误判当前状态。该文件中的旧测试数字是当时的历史快照，不能被当作当前覆盖度。
- 已确认至少 `src/session/driver.rs::EnqueueResult`、`enqueue_while_polling_control` 和 `src/client.rs` 的若干私有 helper 缺少项目 Rustdoc 规则要求的语义说明。本轮只处理触及的生产模块，不借此重排全仓模块。

## 决策一：保留多值头并明确覆盖规则

对默认头和单次连接头分别执行“按名称替换整组值”：在处理一个来源中的某个名称时，先删除目标请求里该名称的全部值，再按来源 `get_all(name)` 的顺序追加全部值。第二个来源（单次连接头）覆盖默认来源的同名整组值，不与默认值混合；其他名称不受影响。协议保留头仍在合并前拒绝，子协议头仍由库最后写入。实现可在 `apply_user_headers` 中以 `keys()` 枚举名称、`remove` 清除旧值、`append` 保留同名多值，无须改变公开签名。

这一规则符合现有“单次连接头覆盖默认头”的文档语义，并保留调用方通过 `HeaderMap::append` 表达的多个值。它不自动合并逗号值、不规范化业务头、不猜测某个头是否应为单值。对 `Authorization` 等安全敏感头仍由调用方提供合法值；库负责原样传递并继续拒绝 `Host`、`Connection`、`Upgrade` 与 `Sec-WebSocket-*`。

| 方案 | 结果 | 取舍 |
| --- | --- | --- |
| 保持 `insert` | 丢失多值 | 不符合 `HeaderMap` 输入能力，拒绝。 |
| 所有来源无条件 `append` | 保留多值，但连接级认证头可能与默认认证头并存 | 改变既有覆盖契约，拒绝。 |
| 每个来源按名称替换整组值 | 保留来源内多值，连接级整组覆盖默认值 | 采用。 |

测试应同时断言默认来源的两个同名值均保留、单次连接来源的两个同名值完整取代默认整组、无关默认头仍保留，以及协议保留头继续被拒绝。至少一条本地握手集成测试应从服务端观察实际收到的多值头，避免只验证内部 `Request` 对象。

## 决策二：保留有界入站策略，写清两种关闭触发条件

保持现有控制帧活性策略：入站队列满时最多暂存正在等待入队的一条业务消息，继续 poll 对端以处理 Ping、Pong 和 Close。此期间若再收到业务数据，立即终止慢消费者路径；若没有额外业务数据且容量迟迟不释放，则在 `no_progress_timeout` 到期时终止。两种触发均尝试发送 `1013`，并以当前 `Timeout` 终态交付。网络或写入失败时不能保证对端实际收到 Close，文档不得承诺它必定送达。

选择此策略是为了同时限制内存和维持控制帧响应。简单停止读取可以等待应用恢复，但也会停止处理 Ping/Close；为任意数量业务消息另建缓冲则破坏当前容量上界。本轮不改动这条已测试的运行时规则，而是增加一个直接调用私有排队 helper 的确定性测试：使入站队列已满、待入队消息阻塞、输入流立即给出另一条业务消息，断言在长期限到期前返回 `SlowConsumer`。现有真实 WebSocket 的 Ping/Pong、`1013`、超时和恢复路径测试继续保留。

两份用户指南须明确：容量若及时释放，等待中的消息可入队；继续到来的额外业务数据会提前触发关闭；即使没有额外数据，配置的无进展期限仍会触发关闭。`Timeout` 是当前公开错误分类，不把它写成业务处理超时或对端确认。

## 文档与 Rustdoc

1. 将 `src/lib.rs` 的 `1000` 示例输出改为“协议关闭完成”，在示例附近说明应用仍需按自己的确认和恢复策略判定订阅结果。同步核对其他触及的公开 Rustdoc，不把 `close() == Ok(())` 或关闭码写成业务成功。
2. 为 `src/client.rs` 的头合并 helper 及 `src/session/driver.rs` 中与入站慢消费者路径相关的私有类型、变体和 helper 补英文语义 Rustdoc；核对触及的 `src/session/queue.rs` 私有 helper。描述容量、控制帧和提前关闭条件，不只复述函数名。保持项目现有模块组织和格式配置，不做无关风格重排。
3. 两份 README 说明默认头与单次连接头的整组覆盖规则，并检查语言间 API、状态码和限制一致。两份用户指南同步更新背压行为及多值头用法。文档示例继续以服务自身的事件格式、认证和业务确认策略为前提。
4. 把旧关闭协调设计文档顶部改成“已实施的历史设计记录”，注明其中测试数量是当时快照；更新中英文架构文档及 README 中的链接标签，使现行架构、已实施历史设计、本待实施方案三者的身份清楚。当前详细设计不要求一份新的英文逐字译本；两种语言的现行架构与用法入口仍须语义一致。
