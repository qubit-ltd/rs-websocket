## 2. 现状与证据

### WS-001：验证与期限构造不一致

`src/options/ws_client_options.rs:100-120` 仅要求超时非零。公开 builder 原样接收 `WsSessionLimits`，因此 `close_timeout: Duration::MAX` 或 `no_progress_timeout: Duration::MAX` 可通过构建。

`src/session/ws_session.rs:301` 在公开 `close()` 中直接将 `close_timeout` 加到 Tokio `Instant` 上，溢出可使调用方 panic。`src/session/internal/driver.rs:225、231、265、272、476、552、577` 还有直接期限加法，驱动的 panic 捕获不能替代配置校验，否则错误会归为 `Internal`。实施时按符号搜索重新定位，不依赖行号保持不变。

确认输入为 Rust API 的 `Duration::MAX`；不声称 `u64::MAX` 毫秒在当前 Linux 上必然溢出，也不把配置文件路径的未验证平台行为作为缺陷依据。

### WS-002：文档承诺了实际不可达的连接后决策

`doc/user_guide.md:121`、`doc/user_guide.zh_CN.md:121` 及两版故障表提示：提议子协议后，若服务端未选择，可连接后查看 `selected_subprotocol()` 决定是否接受。

实际 `src/client/internal/handshake.rs:119` 调用的 tungstenite 0.30.0 在存在提议但响应省略子协议头时返回 `NoSubProtocol`，项目将其映射为 `Handshake` / `WsHandshakeFailure::Subprotocol`。不会创建可供判断的会话。`WsSession::selected_subprotocol()` 的 Rustdoc 也需补充成功会话返回 `None` 的边界。

### WS-003：失败路径的等待没有完整边界

`tests/session_tests.rs:664、1035、1503` 一类循环只匹配 Close，没有终止处理 EOF／错误。流结束后继续 `next()` 可能形成无让出的忙循环；每次读取各自加 timeout 无法限制整个循环。

`src/session/ws_session/ws_session_tests.rs:100-131、165-243` 在同步 hook 中执行 `std::sync::Barrier::wait()`，随后无界 `join()`。即使测试使用多线程 Tokio runtime，阻塞当前测试 future 的同步屏障也不能由包裹该 future 的异步 timeout 抢占。

### WS-004：竞争测试实际上串行

`src/tests/session/internal_tests.rs:275-295` 的默认 `#[tokio::test]` 为单线程。异步屏障后的 `queue.close()` 和 `drop(envelope)` 没有让出点，不能同时执行。已有 Pending 入队及唤醒测试继续保留，不因这项覆盖增强认定生产队列存在竞争缺陷。

### WS-005：期限分支的优先级疑点

`src/session/internal/driver.rs:344-372` 的 `biased` select 将 `stream.next()` 放在 deadline 之前。队列满且持续收到就绪的 Ping/Pong 时，期限可能被更早分支持续压过。现有 `src/session/internal/driver/tests.rs:123-145` 使用 pending stream，不能回答该问题。真实 socket 的就绪、缓冲和 Tokio 合作调度是否允许持续触发，仍需实验。

## 3. 总体选择与非目标

采用局部修改：保留 client / options / session / error 分层、单驱动任务、现有队列及终态合并方式。所有公开签名和错误枚举保持不变。

未选方案：重写驱动为新状态机改动过大；添加可选子协议协商策略改变产品行为；引入通用并发测试框架或新时钟抽象超出本轮收益。无需生产下游迁移；本轮检索未发现其他 `rs-*` 生产代码直接依赖本 crate。

不扩展自动重连、代理、压缩、业务确认或内存预算功能；不修改 `rs-web` 生产代码；不整理无关 import、inline、文件结构或历史设计正文。

## 4. WS-001：期限安全

### 构建期

在现有 `WsClientOptions::validate()` 中，保留原有非零和容量关系检查，增加对 `limits.close_timeout` 与 `limits.no_progress_timeout` 的可表示性检查：取一次 `tokio::time::Instant::now()`，对两者分别执行 `checked_add`，任一为 `None` 即返回现有 `WsErrorKind::InvalidConfig`。

不设置随意的固定最大天数，不把超时钳制为其他值或无限期等待。TCP／握手超时目前使用底座的相对 timeout，不因本条目强行改变它们的取值合同。若实施中发现新的可复现溢出路径，记录证据并在同一明确根因内处理。

### 运行期

构建与实际使用有时间间隔，仍须将本轮会话代码的直接 `Instant + Duration` 改为 `checked_add`。各函数使用现有返回类型传播 `InvalidConfig`：

| 位置 | 无法表示期限时的结果 |
| --- | --- |
| `WsSession::close()` | 在发布关闭请求之前返回 `Err(WsError::new(InvalidConfig))`，不部分执行关闭、不缓存伪终态。 |
| `read_loop()` | `ReadResult::Error(InvalidConfig)`，走现有终态发布与资源释放。 |
| `send_envelope()` | `SendResult::Exit(Some(InvalidConfig))`，释放 envelope 容量。 |
| `send_slow_consumer_close()`、`close_sink_and_wait()` | `Some(InvalidConfig)`，交由既有驱动收束流程处理。 |

无需增加新公共 helper 或错误变体。优先在现有函数就地使用 `checked_add`；仅在实际重复足以妨碍正确性时提取私有函数，不新增通用时间子系统。WS-005 若需要绝对 deadline，同样使用受检构造。

测试覆盖默认值、零值、两个字段分别为 `Duration::MAX`、公开 builder 拒绝，以及内部构造会话／驱动的防御性返回。通过现有私有测试入口构造非法内部状态，不扩大生产可见性。

### 兼容性

这是对无效边界配置的行为收紧：原先被接受后可能 panic 的值改为 `InvalidConfig`。正常配置、公开类型和函数签名不变。调用方若设置不可表示的极大时长，应改用有限、符合业务停机目标的值；不使用 `Duration::MAX` 模拟禁用超时。平台可表示范围可能不同，文档不得承诺统一最大数值。

## 5. WS-002：子协议合同对齐

沿用当前严格协商行为，不改变 tungstenite、不增加策略开关。

| 请求／响应 | 当前合同 |
| --- | --- |
| 无子协议提议，服务端也不返回子协议 | 成功会话可返回 `selected_subprotocol() == None`。 |
| 非空提议，服务端选中一个提议值 | 成功会话返回所选值。 |
| 非空提议，合法 101 但省略响应子协议头 | `Handshake` / `WsHandshakeFailure::Subprotocol`；无会话。 |
| 返回未提议值或重复子协议值 | 保持现有拒绝行为。 |

在 `tests/protocol_tests.rs` 的 `ResponseCase` 与原始响应生成器中增加只省略子协议头的场景，复用现有分类断言。另明确验证无提议且无选择时成功返回 `None`；复用现有成功握手 fixture，避免再造 TLS 服务端。

修改两版用户指南的鉴权／子协议段和排障表，以及 `WsSession::selected_subprotocol()`、builder 子协议配置相关 Rustdoc。Rustdoc 用英文，设计与实施记录用中文。README 当前只宣称支持提议，无需为此重写；若发现同一错误承诺，只做对应句子的修正。

## 6. WS-003：让测试失败有界

### Close 等待

在 `tests/session_tests.rs` 复用 `peer_message()`，增加本文件内的 `peer_close()` 辅助函数：循环读取控制帧，对 Close 返回，对 EOF／读取错误立即返回错误，并在整个循环外设置一次 `DEADLINE`。忽略无关帧时保留同一截止时间，不重置预算。

该 helper 只观察 Close；是否 flush 回复仍由各测试原有场景决定，避免改变“刻意不回复 Close”的测试。替换所有同根因循环，包括评审列出的三个位置；不机械替换已经正确处理断连的其他循环。给新 helper 增加 EOF、读取错误、持续无关帧及静默对端的失败路径保护。会导致同步忙循环的探针沿用现有父子测试进程模式，由父进程 wall-clock 截止并终止卡住的子进程，不能仅依赖待测 runtime 内的 timeout。

### 接收竞态 hook

保留现有 hook 的测试专用边界和目标交错，不新增生产 hook。将同步屏障替换为标准通道双向握手：hook 发送“已到达检查点”，发布线程用 `recv_timeout` 等待后发布数据／终态并发送“可继续”；hook 的等待也使用 `recv_timeout`。

双方均以超时或断连结束，并带阶段名称报错；发布线程结束另发完成信号，测试收到完成信号后再 join。完成通知缺失时明确失败，不在错误分支执行无界 join。确保 HookGuard 清理与 owner abort 在失败路径也能执行；可用测试局部 guard，不更改生产 Drop 行为。

## 7. WS-004：可观察的并发覆盖

保留或拆成两个确定性用例，分别验证“先关闭后释放 envelope”和“先释放 envelope 后关闭”。另将竞争用例改为多线程 Tokio runtime，用两个独立任务及异步起跑屏障释放 `close()` 与 `drop(envelope)`，使其具备跨线程重叠执行的条件；有限重复采样提高调度覆盖，不把重复次数当作证明。

每轮先用已有 poll／oneshot 技术确认多个入队等待者已 Pending，再起跑。所有 join 与握手均有期限。完成后断言 `usage() == (0, 0)`、新发送为 `Closed`、全部等待者有界结束。竞争中若释放容量先发生，等待者可能在关闭前合法入队，结果允许 `Ok(())` 或 `Closed`；不能要求全部返回 `Closed`。只有明确先关闭的用例要求全部等待者返回 `Closed`。测试不能证明所有交错，报告应准确称“跨线程竞争覆盖”，不称形式化无竞争证明。

## 8. WS-005：核查与条件性修复

第一步先核对真实合同：等待的是入站队列容量，Ping/Pong 活跃不能重置这项等待期限。使用已满队列、一个等待消息及保持就绪的控制帧流，检查过期后是否返回 `EnqueueResult::Stalled`。探针必须有独立于 Tokio 被测 future 的外部退出保护；持续就绪流可在 wall-clock 保护期后返回可识别错误，父测试进程再提供最终硬截止。不能用仅包裹同一个 future 的 Tokio timeout 作为唯一保护。

随后使用本地 socket，先确认队列满及待入队，再持续发送 Ping/Pong，记录是否在无容量进展期限后进入 `Timeout` 并尝试 `1013`。发送任务、读取回复与测试收尾均设期限，避免发送端本身被写缓冲阻塞而伪造“持续控制帧就绪”。记录控制帧数量、持续时间和消费状态，区分真实 socket 复现与受控流复现。

证据分支：

1. 有效受控流证明 helper 合同被破坏：允许最小修复，并报告真实 socket 是否复现；不能将仅受控复现描述为已确认的网络攻击路径。
2. 真实连接也复现：同时保留 helper 与公开会话回归，记录实际终态及 Close 观察结果。
3. 未复现或 fixture 不能证明持续就绪前提：保留有效核查证据和结论，不修改生产分支。环境阻断时保留“未完成核查”，不得写已排除或已修复。

确认后的首选修复是在 `biased` select 中保留入队成功与本地关闭的既有优先级，将 deadline 分支移至 `stream.next()` 之前。若仍不能保证到期可观察，再在循环内显式检查受检绝对 deadline。不要单纯去掉 `biased` 引入概率性修复，不扩大为驱动重写。恢复容量与期限同时就绪时仍允许已优先的入队成功；本地关闭与 deadline 同时就绪时保持原有本地关闭优先级。
