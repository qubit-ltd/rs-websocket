# 实施结论：WS-001 与 WS-002

## 范围结果

- **WS-001 已完成。** `WsSendFailure` 字段、构造函数及借用/转移方法现在说明拒绝类别、原消息所有权、返回值和元组顺序；文档明确队列拒绝不表示业务回滚或其他消息的投递结果。签名、属性和格式化行为未变。
- **WS-002 已确认存在高等待者数下的释放扫描开销，并保留条件索引优化。** 等待者超过 128 时建立按 payload 字节分组的 `BTreeMap<usize, BTreeSet<waiter_id>>`。每个 bucket 中以及全部可容纳 bucket 之间仍按最小 waiter ID 选择，保持现有选择顺序；登记、选择、reset、remove 和 close 仍由原队列状态锁协调。等待者数降到 128 或以下时停用索引。切换时通过 `mem::take` 在锁内移出索引，并在解锁后析构，避免批量释放树节点时阻塞队列锁。
- **回归覆盖。** 补充活动索引下跳过不适配前缀、reset 后重新可选、取消已选 waiter 后交接、close 广播，以及峰值回落后的停用检查。容量、零字节、混合预算、取消和关闭等既有断言仍保留。内部测试从违规 `#[path]` 重定向迁至标准 `src/session/tests` 模块路径，未删除测试。

## 性能证据

基线为 `6c2ab2fd5dcb5065028fefad9f0fc0ab2cf9616a`。测量使用 Rust 1.94.0、x86_64 Linux、Intel Xeon E5-2680 v4、release 构建；所有场景均为 7 轮。原始记录和环境信息位于 `doc/evidence/review-20261105T060550147Z-5656d7a6/`。

单线程下，16,384 个不适配前缀等待者后释放预算的 p50，从基线 **76,500 ns** 降至最终候选 **947 ns**，约改善 **98.8%**。对应获准等待者接受 p50 从 **75,108 ns** 降至 **771 ns**。双 worker 并发探针下，16,384 个等待者的释放 p50 从 **134,119 ns** 降至最终候选 **4,107 ns**，约改善 **96.9%**；接受 p50 从 **154,951 ns** 降至 **11,831 ns**。两组均超过计划要求的 30% 改善。

普通取消/关闭控制未显示稳定退化：单线程 16,384 waiter 取消 p50 为基线 **385 ns**、候选 **335 ns**；close p50 为基线 **680,306 ns**、候选 **667,818 ns**。另测峰值从 16,384 回落到阈值时触发的单次取消：候选 7 个样本的 p50 为 **1,471 ns**，p95 为 **540,534 ns**。该 p95 等于单个离群最大样本，只有 7 个样本，不能视作稳健尾延迟估计。整份旧索引在解锁后析构，因此这个取消操作自身仍承担释放内存的时间，但析构不再延长其他队列操作等待状态锁的时间。

索引的结构性内存成本是：每个活动的未通知 waiter 在原 waiter 表之外增加一个 `BTreeSet` ID 节点，每种不同 payload 大小增加一个 `BTreeMap` bucket；超过阈值时另有一次性索引构造分配。索引在 waiter 数回落到 128 或以下时释放。未单独测量分配器层的绝对字节数，实际开销会随 waiter 数和不同 payload 大小数量变化。
