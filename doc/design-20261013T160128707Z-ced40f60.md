# rs-websocket 会话终态与错误契约修复设计

> 写作日期：2026-10-14。本文是本轮评审意见的实施依据；文件名使用用户指定的标识。目标为 `qubit-websocket` 0.1.0。用户允许破坏性 API 变更，本设计不提供旧枚举变体的兼容层。

## 现状与目标

当前驱动在读侧收到对端 Close 后等待写侧结束，但 `run` 将 `ReadResult::Closed(code)` 无条件转为 `WsTermination::Normal { code }`，即使写侧 flush 失败或超时也丢弃其错误（`src/session/driver.rs:93-124`）。同时，收到错误关闭码 `1009` 的互通测试也允许 `Normal`（`tests/web_interop_tests.rs:248-281`）。应用若仅匹配 `Normal` 决定是否恢复，可能把关闭失败或对端拒绝当成成功。现有 Rustdoc 将 `WsErrorKind::Connect` 限定为建连失败，而运行期传输错误及任务异常也映射到它；部分生产辅助函数缺少语义文档。

目标是让终态同时准确表达“关闭握手是否完成”和“对端发了什么关闭码”，让传输错误及内部任务失败各归其类，并使 Rustdoc、两种语言的 README 与用户指南和代码一致。保持队列容量、TLS、握手、Ping/Pong、自动重连边界及 `send` 仅确认入队的既有语义。

## 方案选择

考虑过继续保留 `Normal`，仅把 `1009` 等错误码转成 `Error`。这种做法会丢失对端的结构化关闭码，还把协议握手成功与应用是否接受该状态码混在一起。也考虑过为每种关闭码增加枚举变体，扩展性和调用方匹配成本都较差。本轮采用传输结果与业务判断分离的方案：成功完成关闭握手统一记为 `Closed { code }`，由应用根据业务协议判断 `code`；握手或传输失败记为 `Error`。这是有意的公开 API 破坏性变更。

## 公开契约

```rust
pub enum WsTermination {
    Closed { code: Option<u16> },
    Error { kind: WsErrorKind },
}

pub enum WsErrorKind {
    // 保留其余现有变体；将 Connect 重命名为 Transport。
    Transport,
    Internal,
}
```

- `Closed` 表示驱动观察到完整的协议关闭过程并成功结束所需写操作。`code` 是对端 Close 帧里的原始状态码；`None` 只表示对端未提供状态码，不能由库推断为业务成功。`1000`、`1001`、`1009` 和应用自定义码都保留原值；库不替应用判定是否重试。
- `Error` 表示无法确认关闭握手成功，或读写、协议、超时、驱动任务发生故障。收到对端 Close 后若回复的 flush 失败或超时，终态必须为 `Error`；`receive()` 仍只交付一次终态错误，之后返回 `None`；`close()` 返回相同类别的错误。此分支不再承诺保留对端 Close 码；若应用需要它，应在成功关闭时读取 `Closed.code`，失败时按错误处理。
- `Transport` 涵盖 DNS/TCP 建连失败及已建立连接的底层 I/O 错误；连接阶段 TLS 与握手错误继续按现有 `Tls`、`Handshake` 分类。驱动读写任务的 `JoinError`（含 panic 或异常取消）归 `Internal`，不再误记为传输错误。`Timeout` 仍表示期限届满。`WsErrorKind::Connect` 删除，不保留别名。
- `WsError` 的默认 `Display`/`Debug` 继续脱敏，`source()` 的显式诊断边界不变。`WsSendError` 与队列行为不变。

## 驱动状态合并

在 `src/session/driver.rs` 增加一个只接收 `ReadResult` 与写侧结果的纯函数 `resolve_termination(read_result, write_result) -> WsTermination`，集中实施以下优先级，避免在 `run` 分支里再次遗漏写侧错误。

| 读侧结果 | 写侧结果 | 终态 |
| --- | --- | --- |
| `Closed(code)` | `None` | `Closed { code }` |
| `Closed(_)` | `Some(kind)` | `Error { kind }`；关闭回复失败不能算完成 |
| `Error(kind)` | 任意 | `Error { kind }`；保留先观察到的读侧故障 |
| `LocalClose` | `None` | `Closed { code: None }`；现有本地主动关闭成功语义 |
| `LocalClose` | `Some(kind)` | `Error { kind }` |

`run` 继续先通知队列关闭，再写入唯一终态快照并唤醒等待者。读侧结束后等待写侧仍受 `close_timeout` 限制；等待超时先 abort 写任务，再将 `Timeout` 送入合并函数。写侧先异常结束时 abort 读任务；任务 join 失败映射为 `Internal`。不要为了回传关闭码延长任何截止时间，也不要把 `Closed` 视为业务确认。

## 测试策略

1. 在驱动单元测试中对状态合并函数做穷举表：对端 `1000`、`1009`、无状态码，读侧错误、写侧 `Timeout`、写侧 `Transport`、本地关闭。关键断言是 `Closed(Some(1000)) + Some(Timeout) => Error(Timeout)`。
2. 复用现有 `ControlledSink` 或增加最小的可控 Sink，使对端 Close 后的 flush 确定性返回错误/保持 Pending 至超时；验证写侧结果真实进入合并逻辑。避免依赖 TCP 缓冲区大小或 `sleep` 竞争制造失败。
3. 更新 `tests/session_tests.rs` 的对端先关闭、重复关闭、关闭超时断言；更新 `tests/web_interop_tests.rs` 中 `1009` 的断言为 `Closed { code: Some(1009) }`。保留当前 WS/WSS、队列和 rs-web 互通回归。
4. 运行完整 `cargo test --locked --offline`（含 doctest）、项目配置化 rustfmt、`.infra/bin/style-check.sh`、Clippy 和 Rustdoc。项目共享 `target`，重型 Cargo 命令顺序运行。

## Rustdoc 与双语文档

- 更新 `src/error.rs` 的变体说明：`Closed` 是协议关闭完成，绝非业务成功；`Transport` 涵盖建连与运行期 I/O；`Internal` 包含任务 join 故障。`src/session.rs` 的 `receive()`、`close()`、`termination()` 要说明错误交付和关闭码策略。
- 为本轮触及的 `src/session/driver.rs` 私有状态、合并函数和关闭辅助函数，以及 `src/client/handshake.rs` 的握手辅助函数补充英文语义 Rustdoc，包括错误、超时、所有权和敏感信息边界。对核心公开类型补可由公开 API 编译的示例；不为填充文档做无关文件拆分。
- 同步 `src/lib.rs` 示例、两份 README、两份用户指南与两个命令行示例中受影响的枚举匹配或描述。指南要给出可执行的应用决策样例：`Closed { code: Some(1000) }` 可按示例业务协议视为正常完成，`1009`、`None` 和 `Error` 分别进入应用定义的诊断或恢复路径；不得将这些策略写成库的自动重连承诺。
- 两种语言分别自然组织文字，但错误分类、关闭码语义、操作顺序和限制必须一致。`doc/design.zh_CN.md` 保持历史记录，在开头加入本设计的现行契约入口，不重写历史正文。

## 边界与风险

本轮不修改其他 `rs-*` 仓库；当前扫描未发现它们的生产 Cargo 清单直接依赖本 crate，`rs-web` 仅是本仓库互通测试依赖。公开枚举重命名会使使用 `Normal` 或 `Connect` 的调用方编译失败，迁移说明须明确列出替换方式。`Closed { code: Some(1009) }` 不是“成功”：其含义取决于应用协议。对端 Close 后写侧失败的回归测试必须可重复，不能把仅测试纯函数当成完整行为验证。

## 验收标准

1. 对端先发 Close 而写侧回复失败或超时，`termination()` 为 `Error`，`receive()` 恰好交付一次对应错误，`close()` 不返回成功；测试稳定复现。
2. 对端发送 `1009` 且握手完成，`termination()` 保留 `Closed { code: Some(1009) }`；文档明确该状态需要应用判断，`Normal` 不再出现在现行 API 或指南中。
3. `Connect` 完整迁移为 `Transport`；任务 join 故障归 `Internal`；相关错误说明、测试和迁移指南一致。
4. 本轮涉及的私有 helper、核心公开类型及生命周期 API 的 Rustdoc 完整且示例可编译；中英文 README/指南、现行设计入口与源码一致。
5. 项目格式、风格、Clippy、测试与 Rustdoc 门禁通过；最终 diff 仅含本设计相关文件，不提交或推送。
