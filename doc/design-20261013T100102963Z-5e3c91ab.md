# rs-websocket 配置校验、错误契约与停机文档修复设计

> 日期：2026-10-13。依据：用户已接受本轮评审意见并授权直接产出设计与实施计划。目标仓库为 `/data/working/qubit/rust-common/rs-websocket`；本文只设计本轮改进，不实施代码修改。

## 现状与目标

`qubit-websocket` 0.1.0 使用 Rust 2024、Rust 1.94、Tokio 与 `tokio-tungstenite`，提供有界 WebSocket 客户端。当前测试覆盖本地 WS/WSS、握手、队列、关闭和 `rs-web` 服务端互通；本轮评审运行 `cargo test --locked --offline`，73 项单元及集成测试和 1 项 doctest 通过。未发现其他 `rs-*` 仓库的生产代码直接依赖本 crate，因此不安排跨仓库调用迁移。

本轮处理四个评审点：默认请求头中的协议保留字段延迟到连接时才报错；中英文接入示例无法主动响应服务停机；`WsErrorKind` 中存在不会由当前实现产生、却被指南列为可诊断结果的类别；格式检查命令没有使用项目配置。目标是让构建期校验、实际错误结果和文档示例一致，同时保留现有传输、TLS、队列与关闭行为。

## 方案决策

### 1. 默认请求头在 `build()` 时校验

`WsClientBuilder::headers` 接受的默认 `HeaderMap` 在 `build()` 时检查。沿用现有的 `is_reserved_header` 判定：`Host`、`Connection`、`Upgrade` 和全部 `Sec-WebSocket-*` 字段由协议栈管理，大小写不影响判断。遇到任意保留字段，`build()` 返回 `WsErrorKind::InvalidConfig`；不建立 TCP 连接，也不记录头值。普通默认头和 `connect_with` 的连接级普通头继续按现有顺序覆盖。连接级头只能在 `connect_with` 时取得，仍在建立 TCP 连接之前拒绝其保留字段。

在 `src/client.rs` 提取供构建和请求组装共同使用的 `validate_user_headers(&HeaderMap) -> Result<(), WsError>`；`apply_user_headers` 先调用它再插入，避免两处保留头规则漂移。`WsClientOptions::validate()` 继续只负责限额与超时等数值约束，其 Rustdoc 保持这一准确边界；`WsClientBuilder::build()` 顺序调用数值校验、子协议校验、默认头校验。`connect_socket` 保持现有请求组装时的校验，不改变公开 API。

对比过两个做法：把全部协议校验移入 `WsClientOptions::validate()` 会扩大该公开方法的既有语义并牵动模块职责；仅在 `build()` 另写一份判断容易与连接期规则分叉。共用私有校验函数的变更范围最小。

### 2. 停机示例给出可运行的取消路径

两份 README 和两份用户指南沿用“worker 订阅持续事件流”的场景。基础函数由应用传入 `tokio::sync::oneshot::Receiver<()>`；应用保留 `Sender<()>`，停机时发送一次信号。接收循环用 `tokio::select!` 同时等待停机信号与 `session.receive()`；信号到达或发送端被释放时退出循环，再调用 `session.close().await`，最后检查 `termination()`。示例明确：`close()` 可能返回已存在的终态错误或 `Timeout`，不能把队列入队当作对端处理确认。

README 安装片段为 Tokio 启用 `sync`，与示例所用的 `oneshot` 一致。指南补齐 worker 启动方如何建立通道、持有停机发送端、发信号并等待任务结束，以及 `WsSender` 生产者应先停止、再关闭会话的顺序。指南用同一代码路径解释对端主动关闭、传输错误和本地主动停机的不同可观察结果；两版语义一致，中文独立组织表述。仓库示例 `examples/ws_client.rs`、`examples/wss_client.rs` 仍是手工运行的客户端示例，不把它们误述为服务停机端到端验证。

此方案不新增公开取消 API 或自动重连。`oneshot` 适合单个会话所属 worker；需要广播停机的应用可在自己的任务管理层分发信号。取消 `receive()` future 本身只取消该次等待，真正的会话关闭由随后的 `close()` 完成。不能靠 `drop(session)` 替代显式等待，因为现有 `WsSender` 也持有会话所有权，最后一个控制句柄释放才触发后台关闭。

### 3. 收紧 `WsErrorKind` 契约

删除公开 `WsErrorKind::Cancelled` 与 `WsErrorKind::Closed`。当前 `src/` 没有生成两者的路径：取消异步操作表现为 future 被丢弃；已关闭的发送队列通过独立的 `WsSendError::Closed` 报告。由于用户允许破坏性变更，删除不会实际产生的枚举变体，比保留并称为“可诊断”更清楚。继续保留 `WsErrorKind::Internal`，它在驱动任务异常结束的路径使用。

两份指南的错误速查表、Rustdoc 和相关设计说明应区分三种结果：`WsErrorKind` 表示建连或会话终态错误，`WsSendError::Closed` 表示发送不再被接纳，future 取消本身不返回 `WsError`。检查所有源码、测试、示例、双语 README 和指南中对移除变体的引用，并在 README 的迁移说明列出这一破坏性变更。`doc/design.zh_CN.md` 是首版设计记录；在其开头补当前设计链接，避免历史“取消可区分”描述被当作现行 API 承诺。

### 4. 使用项目格式配置验证风格

本轮评审执行无项目配置的 `cargo fmt --all -- --check` 得到差异；复核后，`cargo fmt --all -- --check --config-path .infra/style/rustfmt.toml` 退出码为 0，稳定工具链仅提示配置中的部分 nightly 选项无法启用。因此先前的“格式未通过”是检查命令选错，不是已证实的代码风格缺陷。本轮不做全库格式化。实施中仅按项目的 `.infra/bin/align-ci.sh` 整理本轮实际改动，再用配置化 rustfmt 和 `.infra/bin/style-check.sh` 核验；若整理触及无关文件，检查原因与范围，不把无关改动纳入本轮。

## 非目标和风险

不改变 WS/WSS 握手、TLS 信任根、内存限额、队列调度、协议控制帧与关闭协调；不添加服务端、代理、自动重连或业务确认。不调整 `rs-web` 生产代码。删除枚举变体会使依赖它们进行穷举匹配的下游代码无法编译，须在迁移说明中明示；当前本地 `rs-*` 检索未发现生产依赖。服务停机示例依赖应用正确保留并发送停机信号，文档需要清楚标注这一责任。

## 验收标准

1. 含保留字段的默认头在 `WsClientBuilder::build()` 返回 `InvalidConfig`；`connect_with` 的保留头在网络连接前返回相同类别；普通头覆盖语义保留。
2. 双语 README 和指南能从 worker 启动走到停机信号、主动 `close()`、终态检查与任务回收；示例所需 Tokio 特性、公开符号及可观察结果准确，代码片段经过编译或等效示例验证。
3. `WsErrorKind::Cancelled`、`WsErrorKind::Closed` 从当前公开 API 和现行文档中移除；`WsSendError::Closed` 及实际错误行为保持。
4. 使用项目 rustfmt 配置的检查、项目风格检查、相关测试、完整 `cargo test --locked --offline`、Rustdoc 与最终 diff 检查通过；实施改动只涉及上述任务范围。
